# V2

For the most part, v2 is meant to be a drop-in replacement to v1. It is also, much faster.

This might also be genuinely the first multi-threaded and classically stateful nvim lua plugin.

My hope is that other extension authors, and perhaps the nvim core team might be able to derive something of value from both its successes and failures.

---

## Technical Deep Dive

coq v2 is a rewrite to multi-threaded lua, with each completion source having persistent state inside their respective luajit threads.

Needless to say, writing stateful multi-threaded, async programs is non-trivial.

Some complications include: Most of the APIs are not available off of the main thread, including anything that prints to the statusline.

So where do you even begin? On solid foundations.

### Designing for Interruptible Concurrency

The core primitives borrow much from [`trio`](https://trio.readthedocs.io/en/stable/) because structured concurrency prevents intractable control flows, and `golang` because, well. `lua` 5.1 like `go` is a simple language, without much sugar in the way of controlflows.

#### Handling of interrupts: Userspace `defer`

- Like with coq v1, I wanted each keystroke to trigger a completion, without any debouncing. This means that we needed to support cancellation, where we interrupt any inflight completion work, **across thread boundaries**.

- Its easy to implement golang's [defer](https://github.com/ms-jpq/coq_nvim/blob/fda7a0fa88c90ad69fd83175d9eb79f0d0931491/lua/coq/lib/init.lua#L42) in userspace.
  - Python like [Error groups](https://peps.python.org/pep-0654/) can be used to aggregate errors from inside each defer, and the main body.

- Both `defer` and `error group` have well understood semantics.

```lua
local x = lib.scope(function(defer)
  defer(function()
    -- ...
  end)

  -- ...
end)
```

- In lieu of having lua 5.4's [`coroutine.close`](https://www.lua.org/manual/5.4/manual.html#pdf-coroutine.close), we can propagate `defer` through iteration as well.

```lua
local propagated_close, iter = closable.iter(function(defer)
  local close, lines = read_a_file()
  defer(close)

  for x in lines do
    coroutine.yield -- ...
  end
end)
```

#### Implicit State Machines: Async Trampoline

- It is well understood that the major win of `async` programming is that it's fantastic for making [certain kinds of state machines](https://rust-lang.github.io/async-book/02_execution/02_future.html).

- It is possible to implement a trivial async mechanism [like so](https://github.com/ms-jpq/shell_rc/blob/eda53841d5a5b4bd0fc517efe1952a8d4dd4e258/layers/posix/home/.config/nvim/lua/go/async.lua#L3): Build a simple `future` via implementing await by wrapping over `coroutine.yield` and resolve by `coroutine.resume`.

```lua
-- think ~> node:util.promisify
local fs_stat = async.awaitify(vim.uv.fs_stat)

-- ✅ works
local stat = fs_stat(path)
```

- Unfortunately, since Lua lacks symmetric coroutines like that of Ruby's [`fiber.transfer`](https://docs.ruby-lang.org/en/master/Fiber.html#method-i-transfer), this means that we cannot naively correlate arbitrary `yield`s with futures, under nesting.

```lua
-- ✅ works
local stat = fs_stat(path)

local iter = coroutine.wrap(function()
  for path in paths do
    -- ❌ does not work
    local stat = fs_stat(path)

    coroutine.yield -- ...
  end
end)
```

- I have not found a more elegant solution to this problem, other than to introduce a [trampoline mechanism](https://github.com/ms-jpq/coq_nvim/blob/fda7a0fa88c90ad69fd83175d9eb79f0d0931491/lua/coq/lib/async/_runtime.lua#L171), which is a drop-in replacement of lua's [`coroutine.wrap`](https://www.lua.org/manual/5.1/manual.html#pdf-coroutine.wrap).

- The future implementation uses a sentinel value for await's `yield`s, and the trampoline bubbles these up the stack. There is no magic.

```lua
local iter = async.wrap(function()
  for path in paths do
    -- ✅ works due to trampoline
    local stat = fs_stat(path)

    coroutine.yield -- ...
  end
end)
```

- In terms of performance, each bounce on the trampoline adds about 100ns of overhead (MBA M2), over `coroutine.wrap`.

## AI Usage

None of the prose you read here is vibe coded. I respect your time.

The v1 -> v2 rewrite is partially motivated via the sudden loss of my day job to AI. My employer got acquired by Anthropic, and I suddenly had to go from ~ 0% AI usage, to "oh god, I need to either find a new job or become a vibecoder".

Before I could live with being a vibe coder, I wanted to answer the burning question that I had, which is "is it actually possible to write good code using AI".

So, most of the code here in v2 is produced via LLM, but in a perhaps atypical way: by treating LLM agents like IDE++.

When I write code that I care about by hand, I will often invest exorbitantly on rewriting the core interfaces over and over and over again until something good comes out the other end of the process. I see the rewriting of coq (which I have done at least 3-4 times now, including this time, and before coq hit v1) as another extension of this incremental refinement process.

Vibes:

### Mechanical Speed

To this end of iteratively refactorings, using LLMs is probably a 2-3x speed up over what my fingers can do.

The biggest speed up is in writing tests, and tedious multi-file changes, say everytime I changed the core async primitives.

### Code Quality

As somebody who perhaps has had too much pride in the code that I wrote. I think being able to do certain things faster gives you more time to focus on the things that matter more to you.

However, since this is pretty much a solo maintainer project. I do not have any external pressure on either timeline, or scope. I do now think that given equivalent amount of time, I can probably ship higher quality code using LLMs, than without. Only if because normally I write far too little tests.

### Skill Acquisition / Atrophy

My biggest concern for long term LLM usage is that the skills that I have invested so many years of my life into would become debased, not even in the job market sense of the term.

The concern is still there, and I don't know how much my overall experience of re-writing coq using LLMs has alleviate that by much. The bullcase is that by virtue of being able to iterate faster, the learnings through having more cycles would offset the loss from being more detached from each.

The pessimist in me though, figures that there will be much less space for accidental learnings, the kind you acquire through casual struggles.
